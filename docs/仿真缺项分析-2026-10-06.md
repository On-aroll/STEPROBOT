# 仿真模拟缺项分析（2026-10-06）

> 问题：要做仿真模拟，还欠缺什么？
> 方法：把「仿真」拆成三条**互不替代**的路线，逐条列出已有与缺项。每条缺项都附实测依据与可复现命令，**推断与实测分开标注**。
> 边界：本机是 Linux，本文所有结论均为**文件层核对**，不含任何软件运行验证。

---

## 0. 结论先说

| 路线 | 本机能否跑 | 卡在哪 |
|---|---|---|
| **A · Studio 官方虚拟控制器** | ❌ **不能** | 平台是 Windows（硬阻断）；另有控制器整机配置缺失、授权未核验、界面验收未做 |
| **B · 真机轴虚拟** | ❌ **不能** | 需要真机在线；本机无真机、无网段 |
| **C · 自建可编程仿真** | ⚠️ **可行，但缺 3 样关键输入** | 参数口径未定、关节限位缺失、工具 TCP 未标定；软件栈需现装 |
| **D · Ubuntu 原生 SDK**（§9 追加） | ⚠️ **可行，先装 32 位运行库** | 官方有 Linux 版 C++ SDK；但**仿真器仍只有 Windows 版** |

**最要紧的一句**：三条路线里，**只有 C 线能在这台机器上落地**；而 C 线缺的不是"代码"，是**三组数字**——连杆参数的口径、关节限位、工具 TCP。这三组数字**没有任何一份文档给全**。

---

## 1. 先说一个容易搞混的前提

三种「仿真」不是一回事，缺的东西也不一样：

- **A 线**要的是：Studio 装好 + 授权有效 + 虚拟控制器起得来 + SR175-3200 系统能在里面建起来。缺的是**环境与配置**。
- **B 线**要的是：真控制器在线 + 断使能 + 勾选轴虚拟。缺的是**硬件**。
- **C 线**要的是：**机器人模型 + 运动学 + 轨迹语义**。缺的是**数据**。

`Project/test0927/SRSystemFile/ConfigureFiles/RobotParameter.xml`（10,911 B）里有控制器的**连杆几何参数**：

| `comboBoxWristNumb` | 3 |

| `textBoxSRDistBase1_2X` | 330 |
| `textBoxSRDistBase1_2Z` | 629.5 |

| `textBoxSRDistWrist1_2` | 1511 |
| `textBoxSRDistWrist2_TCP` | 225 |
| `textBoxSRRotBase1` / `SRRotBase2` / `SRRotBase3` | 0.0 / 0 / 0.0 |
| `textBoxSRRotWrist1` / `SRRotWrist2` / `SRRotWrist3` | 0.0 / 0.0 / 0.0 |

**这与《STEP机器人研究上手地图》§9.2 的结论不同。** 该地图说"通用手册里不存在你机型的 DH 数值，只能从真机示教器读或用 `eDHParamSet` 要"。实测：**数值确实存在于配置文件里**，不必从真机读。这是本次核对推翻的一条旧结论。

**② 零位数据**

`ConfigureFiles/HomingData.xml`（1,866 B）有六轴的 `MultiTurns` / `SingleTurn` / `Resolution`，每轴 `Resolution = 131072`。这是编码器计数与关节角的换算依据。

**③ 三维几何（可用源）**

`_extract/cad-original/SR175-3200 演示模型/` 16 个文件：`J0`~`J6` 分件 SLDPRT、总装 SLDASM、`3D包络`、`cable1/2`，以及 **73,038,249 B 的整体 `.STEP`**。这份是**可分件、可转换**的几何源。

**④ 轨迹语义（文本齐备）**

`_extract/studio_txt/STEP机器人用户编程手册-1.8.1.20241015.txt` 等，含 `PTP / Lin / Circ / CircleAngle / Spline`、`DYNAMIC` 12 量、`Ovl` 圆滑语义。另有一个 92 字节的示例程序 `program0.srp`：

```
WHILE(TRUE)DO
PTP(ap0,NULL,NULL,Default,WORLD);
PTP(ap1,NULL,NULL,Default,WORLD);
END_WHILE
```

**⑤ 工具链** — 本机 `uv` 可用（`/home/bonvoyage/.local/bin/uv`）；系统 `python3`（3.12.3）已有 `numpy 1.26.4` + `scipy 1.11.4`。

### 3.2 缺项 —— 三组数字 + 一个软件栈

**① 连杆参数的「口径」未定（最关键）**

`RobotParameter.xml` 那组 `SRDist*` / `SRRot*` **不是标准 DH**（没有 `alpha / a / d / theta` 命名），而且**六个 `SRRot*` 全是 0.0**——旋转型偏移在这个文件里没有体现。所以：

- **不能**直接把这张表当 DH 表用。
- `SRDistBase1_2X / _2Z`、`SRDistBase2_3Z` 这种 X/Z 分量的命名，暗示它是一套**位置向量 + 旋转量**的参数化，但**分量到 DH 的映射规则没有找到任何文档**。
- 各组距离之和 629.5 + 1335 + 300 + 1511 + 225 = 4000.5 mm；机型标称 3200。**这两个数不是一回事**（3200 应是工作半径，4000.5 含底座与 TCP 偏置）——但这一点是**推断，未验证**。

→ **必须做的**：在 Windows 上开 Studio，进 3.11.3「DH 参数」界面把界面显示的值抄下来，与这份 `RobotParameter.xml` 对照，才能定下口径。**这是 C 线动工前唯一的前置动作。**

**② `srlib` 不能当几何源** ⚠️ **本次新发现**

`SR175-3200.srlib` 实际是个 **ZIP 包**，内含 10 个条目：9 个网格（`A1`~`A6`、`B1`、`B2`、`Base`，合计约 35 MB STL）+ 1 个 `ModelConfigData.xml`（4,029 B）。

**但 10 个条目全部加密**（ZIP 加密标志位 = 1），无密码无法解出——网格和配置都取不出来。

→ 所以 C 线的几何必须走 `_extract/cad-original/` 那份 CAD，**不要指望从 srlib 里掏**。

**③ 关节限位没找到**

`ConfigureFiles/SystemConfig.xml` 里 `LowerLimit` / `UpperLimit` 都是 **0**，`JointThresholdSet` 是空节点；`WorkSpace.xml` 是笛卡尔空间的默认模板（全零）。

→ 六轴软限位/硬限位**在当前所有文本配置里都找不到**。可能在加密的 srlib 里，也可能要回真机读。**缺了它，自建仿真的可达域与避奇异都算不了。**

**④ 工具 TCP 未标定**

`ConfigureFiles/ToolCalibration.xml`（21,654 B）存在，但内容是**全零模板**（`BaseTool X/Y/Z/A/B/C` 全 0.00）。`SRSystemFile/Models/TOOL_TYPE4.tool` 里也没有可用的 TCP 数值。

→ **缺了它，`getCartPosWorld()` 的读数与仿真对不上，校准这一步做不了。**

**⑤ 仿真软件栈基本空白**

| 库 | 状态 |
|---|---|
| `numpy 1.26.4` / `scipy 1.11.4` | ✅ 仅系统 `python3`（3.12.3）有 |
| managed python 3.13.12 | ❌ 无 numpy |
| `pinocchio` | ❌ 无 |
| `mujoco` | ❌ 无 |
| `pybullet` | ❌ 无 |
| `roboticstoolbox` | ❌ 无 |
| `trimesh` | ❌ 无 |
| `conda` | ❌ 无 |
| `uv` | ✅ 可用 |

**⑥ 没有 URDF / xacro** — 全项目 0 个。自建仿真的模型描述格式要自己定。

**⑦ 没有 STEP→网格 的转换工具** — `FreeCAD` / `openscad` / `assimp` / `meshlab` / `gmsh` **全无**。那份 73 MB 的 `.STEP` 在本机**打不开**。

**⑧ 没有校准基准** — 校准要求"仿真算出的 XYZABC 与真机/虚拟控制器读数对上"。现在真机无网段（`192.168.39.220` 不可达）、虚拟控制器跑不了 → **没有任何参照真值**。

## 9. 追加（2026-10-06 21:45）：Studio 没有 Linux 版，但 SDK 有

起因：用户问「有没有 Ubuntu 版的 STEP Studio？如果只有 Windows 版，那我得换环境」。

**答案：STEPStudio 确认只有 Windows 版；但 C++ SDK 有官方 Linux 构建。这是两件独立的事。**

### 9.1 STEPStudio：三条独立证据指向「只有 Windows」

1. **官方文档全库检索**：36 份文本里 `Ubuntu` / `Linux` / `银河麒麟` / `中标麒麟` / `统信UOS` / `deepin` / `国产操作系统` / `跨平台` —— **全部 0 命中**。
   （注意：单搜「统信」有 1 次命中，逐行核对是「系**统信**息」被切出来的**误命中**，不是发行版。）
2. **说明书 1.2 节原文**：「安装包为 **exe** 格式文件，双击可启动安装程序」，默认目录 `C:\Program Files (x86)\STEPStudio 4.7.0`。1.1「推荐配置」只列 CPU / 内存 / 显卡（i7-14700K / 32GB / RTX 4070Ti），**没有操作系统一项**。
3. **官方下载页实测抓取**（`https://www.stepelectric.com/Download.html`，2026-10-06）。机器人相关下载**全部**如下：

   | 名称 | 格式 | 大小 |
   |---|---|---|
   | `STEPStudio 4.6.1` | **exe** | 1.0 GB |
   | `SR.SDK_C++_X86_Win_V2.4.1.20250801_1013` | zip | 1.7 MB |
   | `SR.SDK_C++_X86_Linux_V2.4.1.20250801_1013` | zip | 872 KB |
   | `SR.SDK_C++_X64_Win_V2.4.1.20250801_1013` | zip | 2.4 MB |

   → **STEPStudio 只有 exe，没有 Linux 版**；且官网列的是 **4.6.1**，没有项目里那份 4.7.0。
   官方新闻（V4.5 功能亮点、2026-09 CAM 报道）也**只字未提** Linux 或国产操作系统。

### 9.2 但 C++ SDK 有 Linux 构建（新信息）

已从官方下载并落盘到项目：`SR.SDK_C++_X86_Linux_V2.4.1.20250801_1013.zip`（892,882 B，SHA-256 `2f5cdebd38849a7a7504246fdae47feba64a71f49b4bda21a8cd8eb5ef435fe0`），解包目录同名，另存一份到 `_extract/sdk/`。

> 下载方式：官网 CDN 直链会返回 **403**，需先带 UA 访问下载页建立会话，再带 cookie + Referer 取文件（与项目文档里记录的现象一致）。

包内 5 个文件：

| 文件 | 大小 | 与 Windows x64 版的关系 |
|---|---|---|
| `RobotCom.hpp` | 29,849 B | SHA-256 与 Windows 版**完全一致** |
| `ControlMsgData.hpp` | 71,477 B | SHA-256 与 Windows 版**完全一致** |
| `EasyTcpClient.hpp` | 1,594 B | SHA-256 与 Windows 版**完全一致** |
| `libSTEPROBOT20250801_1013.so` | 1,667,176 B | Release |
| `libSTEPROBOT20250801_1013d.so` | 1,667,176 B | 与 Release **内容完全相同**（同一 SHA-256 `78ce6b49aa92b89722246932a44b49f79e36ff9174c1c327f10f79490b951456`，只是文件名带 `d`） |

**三个头文件与项目里 Windows x64 版逐字节相同** → 接口一致，C++ 代码可移植。

`.so` 实测：

- `ELF 32-bit LSB shared object, Intel 80386` —— **是 32 位，不是 x86-64**。
- 导出 **1,361 个符号**，命名空间 `STEPROBOTSDK::RobotComClient`，含 `SDKVersion` / `ConnectStatus` / `getAxisPos` / `getCartPos` / `EnableMotorCmd` / `SetModeCmd` / `OverrideSetCmd` / `getRobotDI`/`DO`/`AI`/`AO` 等，与手册接口对得上。
- 依赖：`libstdc++.so.6`、`libm.so.6`、`libgcc_s.so.1`、`libc.so.6`、**`ld-linux.so.2`**（32 位加载器）。
- 要求 **GLIBC ≥ 2.34**（本机 glibc 2.39，满足）。

### 9.3 于是多出第四条路线，但它有个硬缺口

**D 线 · Ubuntu 原生 SDK**

- ✅ **能得到**：原生编译、原生连接控制器、读写状态、下发命令 —— **上位机这一层在 Linux 上是通的**。
- ❌ **得不到**：**Studio 的虚拟控制器**。仿真器只有 Windows 版。
- ⚠️ 本机还差：**32 位运行库没装**。实测 `/lib/ld-linux.so.2` 与 `/usr/lib32/libstdc++.so.6` **均缺失** → 需 `dpkg --add-architecture i386` 后装 `libc6:i386 libstdc++6:i386`（或 `g++-multilib`）。

**所以环境选择的实质是：**

| 你想要什么 | 只能用什么 |
|---|---|
| Studio 的离线编程 / 仿真界面 | **Windows**（无替代） |
| 程序化驱动机器人（读状态、下发命令） | Ubuntu 原生**可行** |
| 在 Linux 上做**仿真** | 只能走 C 线自建；或把 Windows 装进虚拟机跑虚拟控制器、Linux 侧 SDK 经 30312 连过去（**此条为推断，未验证**） |

**两者不冲突**：Studio 与 SDK 是两件独立的事，可以 Windows 跑 Studio、Linux 跑算法。

### 9.4 对 §6「先补这四样」的修正

原文把「上 Windows 机器」列为第 1 优先。现在要分目的：

- 目的是**仿真** → 仍然需要 Windows，Studio 是唯一仿真器，没有替代品。
- 目的是**连真机做算法** → Ubuntu 原生就够，**先装 32 位运行库即可开工**，不必换环境。

也就是说：**「换环境」不是二选一，而是取决于你要的是仿真还是驱动。**

## 10. 追加（2026-10-06 22:00）：关于「仿真画面与真机相互映射」

用户目标原话：**「仿真画面与我的真实机器人他俩是相互映射的」**，问「是不是还得 Windows」。

### 10.1 先把「相互映射」拆成两个方向

「映射」这个词把两件不同的事糊在一起了，必须拆开才能回答平台问题：

| 方向 | 内容 | 数据流向 |
|---|---|---|
| **真机 → 仿真**（看） | 把真机的关节位姿/状态**实时**喂进 3D 视图 | 机器人 → PC 画面 |
| **仿真 → 真机**（动） | 在仿真里编/生成程序，送到真机上执行 | PC → 机器人 |

两个方向的**平台约束完全不同**，下面分开说。

### 10.2 Studio 官方那条路是怎么实现的（原文）

手册 `1STEPStudio使用说明书V4.7.0.txt` 第 967–988 行原文：

```
连接真实控制器：关闭虚拟控制器后启用/关闭连接的真实控制器
1. 获取机器人控制柜中的 codesys 工程，以下将该工程称为【工程 1】
2. 将提供的 codesys 工程中【虚拟仿真】和【Task_CommToStudio】两个文件拷贝至【工程 1】中；
3. 将修改后的【工程 1】中 CommToStudio 里的 ipAddress 改成电脑的本地的 IP
4. 将【工程 1】下载至机器人控制柜，再重启，然后连接仿真软件，此时仿真软件里只需要
   添加跟真实控制器一样的机型，然后点击连接真实控制器即可。
```

**关键判断（实测口径）：这不是一个软件里的开关，而是一次对控制柜的下厂改动。** 要满足三个前提：

1. 你能**拿到控制柜的 CODESYS 工程**（这是控制柜里的 PLC 程序，正常不在随机资料里）；
2. 厂商**提供**了 `【虚拟仿真】` 与 `【Task_CommToStudio】` 这两个 CODESYS 文件；
3. 你有能力把改过的工程**下载回控制柜并重启**（涉及停机、影响产线）。

### 10.3 手册里"数据交互"到底是什么（重要，别过度解读）

手册第六章目录（第 299–306 行）：

```
第六章 真机连接与数据交互
  6.1 真机连接
  6.2 FTP 协议文件传输
  6.3 STEPStudio 数据交互
      6.3.1 前置条件与连接
      6.3.2 文件传输
      6.3.3 在线比较
      6.3.4 一键移机
```

第 2497–2500 行的章首说明也确认：6.3 是「STEPStudio 内部的【文件传输】功能，可实现文件传输、在线比较、一键移机」。

**也就是说：官方手册里的"数据交互"= 工程文件的同步（传文件、比对版本、整站搬迁），不是"实时位姿镜像"。** 你要的那种"画面上机器人跟着真机动"的能力，手册里**没有对应章节**。

关键词检索（本文件实测，见 §8 复现命令）：

| 关键词 | 命中 | 含义 |
|---|---|---|
| `数字孪生` | **0** | 手册无此概念 |
| `虚实` | **0** | 同上 |
| `监控` | **0** | 手册无实时监控章节 |
| `采集` / `录制` | **0** / **0** | 无数据采集/回放 |
| `CODESYS` | **0** | 正文里连这个词都没出现（只在第 2 章的截图式描述里以中文"codesys 工程"出现） |
| `Task_CommToStudio` | 1 | 只在 10.2 那四步里出现一次 |
| `真实控制器` | 4 | 只覆盖"连接/断开" |
| `二次开发` / `插件` / `API` / `接口` | **0 / 0 / 0 / 0**（全 36 份语料） | **Studio 不对外提供编程接口** |

**结论：厂商宣传里的"数字孪生"（见 V4.5 新闻稿）在 4.7.0 手册里查不到可操作章节。** 手册能兑现的上限是「连接真实控制器 + 文件传输/在线比较/一键移机」。宣传与手册之间这道落差，需要你直接问厂商要说法。

### 10.4 回答：是不是必须 Windows

**分方向回答，答案不一样：**

| 你的"映射"实际指 | 是否必须 Windows | 原因 |
|---|---|---|
| 真机状态 → **Studio 的 3D 画面** | **是** | Studio 只有 Windows 版（§9.1 三条独立证据）；且还要改控制柜 CODESYS 工程 |
| 真机状态 → **自建 3D 画面** | **否** | Linux 原生 SDK 能读状态（D 线），画面自己画（Pinocchio/Meshcat/任意 3D 库） |
| **仿真 → 真机** 下发/驱动 | **否**（但画面没了） | Linux SDK 能直接下发命令；Studio 那条（一键移机）仍是 Windows 客户端 |
| 在 Studio 里做**离线编程 + 仿真** | **是** | Studio 无替代品（§9.3） |

**一句话：绑住你的不是"镜像"这件事，而是"Studio 这块界面"。** 数据面（读状态、下命令）在 Linux 上是通的；画面面（Studio 的 3D + 离线编程）只有 Windows。

### 10.5 三条可选落地路径

| 目标 | 路径 | 平台 | 风险/前提 |
|---|---|---|---|
| 真机状态 → 自建 3D 画面 | Ubuntu + Linux SDK 轮询位姿 → 自建渲染 | **Linux 够** | 需自写渲染与坐标对齐；无 Studio 的离线编程 |
| 真机状态 → Studio 3D 画面 | Studio「连接真实控制器」 | **Windows 必须** | 需改控制柜 CODESYS 工程 + 停机重启 |
| 仿真/离线编程 → 真机 | Studio 一键移机；或 SDK 直接下发 | Win / Linux 各一条 | 两条路互不替代 |

### 10.6 需要你拍板 / 需要问厂商的

1. **你要的"映射"是"看"还是"控"？** —— 只看状态、还是要从画面反过来驱动机器人？这直接决定平台。
2. **3D 画面是不是非 Studio 不可？** —— 如果只是要"看见机器人动"，自建画面 + Linux SDK 可以完全不碰 Windows。
3. **厂商能否提供控制柜的 CODESYS 工程**（含 `【虚拟仿真】`、`【Task_CommToStudio】`）？—— 拿不到这两份文件，Studio 那条"连接真实控制器"就走不通，无论什么系统。
4. **端口冲突**（**推断，未验证**）：SDK 走 30312 且**同时只允许 1 个客户端**。Studio 连真机用的是 CommToStudio 任务，是否与 30312 抢占，手册没写 —— 若要同时跑 Studio 和自研程序，需向厂商确认。

### 11.3 这条结论修正了什么

**所以 C 线（自建仿真）的卡点，从"几何"移到了"运动学参数"。**

### 11.4 关于「换成 Windows」

**几何这一条，不构成换 Windows 的理由。** 换不换仍然取决于 §10 那张表：

| 你要的 | 平台 |
|---|---|
| 真机状态 → **Studio 的 3D 画面**（现成软件、现成画面） | 必须 Windows |
| 真机状态 → **自建 3D 画面** | **Linux 够**（几何已就位，SDK 有 Linux 版） |
| **Studio 的离线编程 + 仿真** | 必须 Windows（Studio 无替代品） |
| 自己写算法、驱动机器人 | Linux 够 |

现在多了一个实测依据：**"自建画面"这条路的门槛比之前估计的低**——
不是"从零建模型"，而是"已经有 14 个分好件的网格，只差把关节轴线标出来"。

### 11.5 现在真正缺的是什么

不是几何，是**运动学**：

1. **关节轴线位置与方向** —— STEP 只给了零件在某个固定演示姿态下的形状，没给旋转轴。要从 CAD 配合关系提取，或从连杆几何反推。
2. **装配坐标系 ↔ 控制坐标系对齐** —— 当前是 SolidWorks 装配系，与机器人基坐标系不同（本体实测主要延展在 Y ∈ [-771, 1684]、Z ∈ [-2127, 878] mm）。
3. **连杆参数口径**（§3 原有缺项，未变）
4. **关节限位**（§3 原有缺项，未变）
5. **工具 TCP**（§3 原有缺项，未变）

**顺带一个观察（未验证）**：装配体处于**某个固定演示姿态**，不是零位。看包围盒链
（J0 → J1 → J2 → J3-x → J4 → J5 → J6 沿 +Y 延展后再折向 −Z），
像是"手臂前伸、腕部朝下"的展示姿势。做动画时需要先把姿态归零，否则首帧就是错的。
